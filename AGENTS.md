# Continuum Workbench — Frontend

> Full ecosystem blueprint: see the [Continuum repo AGENTS.md](https://github.com/projectcontinuum-org/continuum-platform-core/blob/main/AGENTS.md) for the complete architecture reference.

## This Repo

Browser-based IDE for Project Continuum. Turborepo monorepo with 4 Yarn workspaces.

## Workspaces

| Workspace | Package | Purpose |
|-----------|---------|---------|
| `continuum-core/` | `@continuum/core` | Types-only shared library — workflow model, node and run types, status enums. Exports only what `workflow-editor-extension` imports; delete an export when its last import goes |
| `workflow-editor-extension/` | `@continuum/workflow-editor-extension` | Eclipse Theia extension — workflow canvas, node explorer, execution viewer. An open `.cwf` tab reloads when the file changes on disk (asks first if it has unsaved edits); opening a file never writes to it. Every call to the platform goes through the typescript-axios clients in `src/generated/` (`api-server/`, `credentials-server/`), generated from the OpenAPI specs committed in continuum-platform-core `docs/api/` with `yarn generate:api` (`scripts/generate-api-clients.sh`; needs `openapi-generator`). Never edit `src/generated/` by hand and never call `fetch` for the platform: regenerate when the specs change and commit the result. The clients are instantiated once in `src/browser/service/ApiClients.ts` (axios with `validateStatus: () => true`, so a 4xx/5xx is a reply, not an exception; `reply()` wraps it as an `HttpReply` from `src/common/HttpReply.ts`, which the response helpers below read status first). Path parameters are checked with `requirePathSegment` before a call (the generated client encodes them); build RSQL values, MQTT topic levels and SVG data URIs with `src/common/SafeEncoding.ts`; sanitize inline SVG with `src/common/SvgSanitizer.ts` (react-inlinesvg `preProcessor`). Node-output reads go through `DataService`, which never throws for an HTTP or network failure: it returns a `NodeDataResult` (`src/common/NodeDataResult.ts`: `page`, `not-found` for a 404, or `error`), and `TableOutputView` shows "Output not available" for a 404 (not your run, a run too old to have its run id stored, or a run that is gone: the api-server deliberately does not say which). The Node Outputs dialog (`NodeOutputViewer`, opened by double-clicking a node in a run) has an Outputs tab and a Flow Variables tab. Outputs lists data ports plus `$error` (first). Every other `$` key is a platform system key and is never listed as a port: use `dataPortIds` from `src/common/FlowVariables.ts`. The Flow Variables tab (`flow-variables-view/FlowVariablesView.tsx`) shows each node's own `$variable` plus the variables it inherited. The platform does not store inherited variables, so `inheritedFlowVariables` recomputes them from the run snapshot; carried loop values override only at actual entry members, then the member's available values propagate to internal children with normal parent precedence. That function ports continuum-platform-core's `FlowVariableMerger` (orchestration service): change both together, along with their specs. Never read a response body before checking its status. Starting a workflow goes through `WorkflowService.activateWorkflow`, which resolves only when the server returned a workflow id and otherwise rejects with a `StartWorkflowError` (`src/common/StartWorkflowResult.ts`: a message safe to show, from the problem-detail `detail`, Spring's `message` or `error`, or a generic one per status); the Run button then shows `Could not start the workflow. <reason>` instead of "started successfully". Never treat a response as a started workflow before checking `response.ok`. Node and edge execution statuses come from the orchestrator in the run snapshot (`node.data.status`, `edge.data.status`). `NodeStatus` and `EdgeStatus` in `@continuum/core` mirror `ContinuumWorkflowModel` in continuum-platform-core value for value; change both together. How each status looks (label, colour, badge, progress indicator, edge class, broken-wire mark) lives in one table, `src/common/ExecutionStatusPresentation.ts`, used by `BaseNode`, `DummyNode` and `BaseEdge`; `NodeStatusPresentation.tsx` maps its badges to MUI icons and fails to compile if its status values drift from the core enums. `SCHEDULED` (dispatched) shows a clock badge and a dashed border, and the worker's `BUSY` replaces it with the progress spinner. `SKIPPED` and `CANCELLED` nodes are dimmed with a dashed border. A `DELIVERED` edge is solid green, a `BROKEN` edge is a red dashed wire with a cross at its midpoint, and an edge with no status (pending, or a run recorded before edge statuses) is a plain wire. An unknown status is shown as its raw value. Scheduling a workflow stores both the schedule's name and the run snapshot's name as `{workflowName}/{scheduleName}.schedule`, where `scheduleName` is an alphanumeric-only PascalCase name from `src/common/XkcdNameGenerator.ts` (e.g. `GreenOtter37`); the snapshot name becomes a scheduled run's `workflowUri`, so the Workflow Runs tree nests those runs under the workflow node → `scheduleName` child, while manual runs (plain workflow name) nest under a `(manual)` child — the tree normalizes distinct run URIs by stripping the `/<name>.schedule` suffix to group all of a workflow's runs under one node. The Manage Schedules tab fetches all owner schedules and filters client-side by that prefix (with a fallback for pre-existing schedules whose name was just the workflow name). The Runs tree's workflow-node right-click context menu (`WorkflowRunsContextMenu` / commands in `WorkflowRunsCommandContribution`) opens the editor (chaining a one-shot `pendingAction` onto the open via `WorkflowEditorWidgetOptions`), runs, schedules/manages, pauses/resumes all of a workflow's schedules, cancels active runs, refreshes, and copies the workflow path; all actions read the selected `WorkflowNode` from the tree model. Specs: `yarn workspace @continuum/workflow-editor-extension test`; `jsdom` is a devDependency because `SvgSanitizer.spec.ts` needs a DOM, and the file FAILS when jsdom is missing (set `ALLOW_NO_JSDOM=1` to run without it). Git support follows the official Theia IDE (Blueprint): `@theia/scm` + `@theia/scm-extra` (the Source Control view) is populated by the VS Code `git` + `git-base` extensions running on `@theia/plugin-ext` + `@theia/plugin-ext-vscode`; there is no `@theia/git`. The extensions are declared in `continuum-workbench/package.json` `theiaPlugins` (Eclipse-built `eclipse-theia/vscode-builtin-extensions` release assets) and fetched into `plugins/` by `yarn download:plugins`. Use the Eclipse builds, not old open-vsx ones: open-vsx `vscode.git` 1.88 implements an older SCM history API and fails to open repositories (`provider.onDidChangeCurrentHistoryItemRefs is not a function`). `plugin-ext` transitively re-introduces `@theia/debug` and `@theia/test`, so the Debug, Testing, and Outline widgets are all hidden by `HideUnwantedWidgetsContribution` on startup (unregisters their toggle commands in `onStart`, closes them in `onDidInitializeLayout`); `@theia/ai-ide` stays removed — the AI chat window and Ollama provider are bound by `@theia/ai-chat-ui` / `@theia/ai-ollama` with `@theia/ai-core`'s default `AIActivationService`. The Welcome widget (`src/browser/widgets/welcome/ContinuumWelcomeWidget.ts`) Help links: Documentation and Node Development open `https://docs.projectcontinuum.org` (Node Development → `/docs/contributing/create-new-nodes`) in a new tab; Keyboard Shortcuts executes `keymaps:open`, provided by `@theia/keymaps` `1.74.1` (pinned with the other VCS packages), which self-registers the keybindings widget and a default `Ctrl+Alt+,` keybinding |
| `workflow-builder-extension/` | `@continuum/workflow-builder-extension` | Theia AI chat agent "WorkflowBuilder" — a prompt only: discovers nodes, validates and builds the `.cwf` with api-server MCP tools, saves it with Theia's `writeFileContent` live (empty file first, rewritten after each added node); `claude-code/` has the Claude Code twin |
| `continuum-workbench/` | `@continuum/workbench` | Full Theia IDE app (port 3002) |
| `continuum-workbench-thin/` | `@continuum/workbench-thin` | Lightweight variant |

## Build

```bash
yarn install && yarn build && yarn start:workbench
# Open http://localhost:3002
```

## CI

`.github/workflows/ci.yml` runs on every pull request and push to `main`: `yarn install --frozen-lockfile --ignore-scripts` then `yarn test` (the specs of `workflow-editor-extension` and `workflow-builder-extension`; the other workspaces have none). `--frozen-lockfile` fails when `package.json` needs an entry `yarn.lock` does not have, so a dependency added without committing the lockfile cannot pass. It does not fail on leftovers: a removed dependency still passes with its old entries in `yarn.lock`, so regenerate the lockfile in the same change and check that the removed packages are gone from it. Do not set `ALLOW_NO_JSDOM` in CI. Image builds and publishing stay in `build-module.yml` and `on-release.yml`.

## Release Notes

Release notes live in `release_notes/`, one file per version: `RELEASE_NOTES_v<version>.md`, where `<version>` is the `version` in the root `package.json` (the version being prepared). Every change updates that file in the same change; a task is not done while the release notes are stale.

- Never edit the file of a version that has already been released (a `release/<version>` tag exists); if the current version is already released, bump the version or ask first.
- Put the change under "Highlights" (user-visible features and fixes), "CI", "Upgrade notes" (anything a deployer or a client must act on, such as a dependency or `yarn.lock` change) or "Changes", and correct any existing line the change makes untrue.

## README

Every change to a module updates the README.md that documents it, in the same change: the module's own README.md if it has one, otherwise the repository root README.md. Keep what a reader runs or relies on true: module lists and tables, setup and run commands, ports, configuration and environment variables, endpoints, node lists, versions and badges, and project-structure trees. Remove what the change deleted, add what it introduced, and correct anything it made untrue. If no README section is affected, say so in the report instead of skipping the check. Report the task as not done while a README is stale. `workflow-builder-extension/` has its own `README.md`; every other workspace is documented in the root `README.md` (workspace table, Quick Start, Project Structure).

## Stack

React 18, TypeScript 5, Eclipse Theia, React Flow 11, JSONForms, MQTT.js, Yarn + Turborepo, Node >= 20

## Theia versions

Every `@theia/*` dependency in every workspace is pinned to one exact version (no ranges, no `latest`), and `yarn.lock` resolves each to that same version, because Theia packages must be identical to work together (`scripts/theia-versions.spec.js` enforces it; the root `yarn test` runs it). Upgrade all of them together and regenerate `yarn.lock` in the same change.

## Script editor (code intelligence in the node dialog)

A `format: "code"` control whose `language` is `kotlin` gets a native Theia Monaco editor on a temp file in the first workspace folder; the Kotlin extension (`fwcd.kotlin`, pinned in `continuum-workbench/package.json` with a checksum) then serves completion, hover and diagnostics. `CodeEditorRenderer` is the only place that decides: `src/common/script-editor/ScriptEditorRoute.ts` returns native or plain (reasons: other language, no workspace, untrusted). A valid `options.scriptContext` (reported by the node: bindings with name and type, plus the declarations of the types they use) adds the node's names; without one, or with a malformed one (never used in the wrapper), the editor is in basic mode: the wrapper is `fun script(): Any? = run {` with no parameters and no declarations file, so only the Kotlin standard library and Java get completion, hover and diagnostics; everything else uses `MonacoEditorWrapper` with the language from `src/common/DialogEditorLanguage.ts` (Kotlin is registered as `continuum-kotlin-script`, never `kotlin`, so a plain editor does not start the extension).

- Pure, spec'd units live in `src/common/script-editor/` (context parsing, wrapper text, file layout and naming, temp-file store with a lease, startup sweep, hidden-lines controller, cursor clamping); only the glue that touches Theia is in `src/browser/script-editor/` (`TheiaScriptFileSystem`, `NativeMonacoEditorFactory`, `ScriptEditorContribution`, `NativeScriptSession`, `useNativeScriptEditor`, `NativeScriptEditor`). `NativeMonacoEditorFactory` and `HiddenAreaController` are the only users of Theia/Monaco internals (`MonacoEditorProvider.createInline`, `setHiddenAreas`): re-check them on a Theia upgrade.
- Files: `<workspace>/.continuum-scripts/<ctxid>/{Script.kt,ScriptFlowVariables.kt (only with a reported context),.lease}` and `.continuum-scripts/.gitignore` (`*`). The script file is `[@file lines] package ctx<id> [imports] fun script(bindings): Any? = run { <user text> }`; the wrapper lines are hidden and re-established after every edit, and only the user's text is ever stored or shown. The folder is deleted when the dialog closes (editor first, so the language server sees the close); folders with a missing or expired lease (2 minutes, renewed every 30 s) are swept at start and on workspace change. `scripts/seed-kotlin-settings.js` seeds `.continuum-scripts` into `files.exclude`/`search.exclude` (its folder name must equal `SCRIPTS_FOLDER`; a spec checks). It does not touch workspace trust: in an untrusted workspace plugins do not run, so the dialog shows the plain editor with "Trust this workspace to enable code intelligence". Symbolic links under the folder are never followed or deleted; a live editor renews its lease and rewrites its files if another tab swept them; the sweep re-runs every lease expiry. A Theia or Monaco version bump must re-run `continuum-system-tests/suites/ui/kotlin-native.mjs`, which reaches Monaco internals.
- Without a workspace folder, or when the files cannot be written, the dialog falls back to the plain editor (with a one-line note); it never blocks.

## Loop canvas

`LoopNode` uses the shared `ExecutionStatusPresentation.ts` table for status labels, badges, working state and colors; keep status mapping out of loop-specific presentation helpers. A Loop is a portless container and must not expose user-connectable handles; collapsed display edges use invisible, non-connectable side anchors only, and saved edges continue to connect member nodes. Keep the box background translucent and theme-based so crossing edges and member nodes remain visible. Loop dimensions are serialized in node width/height and style fields, and resize dimensions must update during pointer movement while history is committed at resize end. The editor renders the saved/default dimensions while members move; member bounds set explicit resize minimums but must not auto-grow a loop during a drag. The run viewer may size an expanded loop to contain its run-snapshot members. When unparenting a dragged member, derive its canvas coordinate by summing its parent-relative position chain and preserve the final drop point; do not reuse cached `positionAbsolute` values. Loop deletion must ask whether to delete or keep members; kept members are converted to absolute canvas positions before their parent reference is cleared. Member nodes display a nesting-level background color, a small loop icon (top-left), and the parent loop's ID in monospace font (e.g., `#loop-1`) via the `useLoopMembership` hook and `loop-member-depth-N` CSS classes; the parent ID helps color-blind users identify membership and parent relationships; colors derive from MUI palette values and work in both light and dark themes.
