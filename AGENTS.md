# Continuum Workbench — Frontend

> Full ecosystem blueprint: see the [Continuum repo AGENTS.md](https://github.com/projectcontinuum-org/continuum-platform-core/blob/main/AGENTS.md) for the complete architecture reference.

## This Repo

Browser-based IDE for Project Continuum. Turborepo monorepo with 4 Yarn workspaces.

## Workspaces

| Workspace | Package | Purpose |
|-----------|---------|---------|
| `continuum-core/` | `@continuum/core` | Shared React library — models, types, React Flow node components |
| `workflow-editor-extension/` | `@continuum/workflow-editor-extension` | Eclipse Theia extension — workflow canvas, node explorer, execution viewer. An open `.cwf` tab reloads when the file changes on disk (asks first if it has unsaved edits); opening a file never writes to it. Build request URLs, RSQL values, MQTT topic levels and SVG data URIs with `src/common/SafeEncoding.ts`; sanitize inline SVG with `src/common/SvgSanitizer.ts` (react-inlinesvg `preProcessor`). Node-output reads go through `DataService`, which never throws for an HTTP or network failure: it returns a `NodeDataResult` (`src/common/NodeDataResult.ts`: `page`, `not-found` for a 404, or `error`), and `TableOutputView` shows "Output not available" for a 404 (not your run, a run too old to have its run id stored, or a run that is gone: the api-server deliberately does not say which). Never read a response body before checking its status. Starting a workflow goes through `WorkflowService.activateWorkflow`, which resolves only when the server returned a workflow id and otherwise rejects with a `StartWorkflowError` (`src/common/StartWorkflowResult.ts`: a message safe to show, from the problem-detail `detail`, Spring's `message` or `error`, or a generic one per status); the Run button then shows `Could not start the workflow. <reason>` instead of "started successfully". Never treat a response as a started workflow before checking `response.ok`. Node and edge execution statuses come from the orchestrator in the run snapshot (`node.data.status`, `edge.data.status`). `NodeStatus` and `EdgeStatus` in `@continuum/core` mirror `ContinuumWorkflowModel` in continuum-platform-core value for value; change both together. How each status looks (label, colour, badge, progress indicator, edge class, broken-wire mark) lives in one table, `src/common/ExecutionStatusPresentation.ts`, used by `BaseNode`, `DummyNode` and `BaseEdge`; `NodeStatusPresentation.tsx` maps its badges to MUI icons and fails to compile if its status values drift from the core enums. `SCHEDULED` (dispatched) shows a clock badge and a dashed border, and the worker's `BUSY` replaces it with the progress spinner. `SKIPPED` and `CANCELLED` nodes are dimmed with a dashed border. A `DELIVERED` edge is solid green, a `BROKEN` edge is a red dashed wire with a cross at its midpoint, and an edge with no status (pending, or a run recorded before edge statuses) is a plain wire. An unknown status is shown as its raw value. Scheduling a workflow stores both the schedule's name and the run snapshot's name as `{workflowName}/{scheduleName}.schedule`, where `scheduleName` is an alphanumeric-only PascalCase name from `src/common/XkcdNameGenerator.ts` (e.g. `GreenOtter37`); the snapshot name becomes a scheduled run's `workflowUri`, so the Workflow Runs tree nests those runs under the workflow node → `scheduleName` child, while manual runs (plain workflow name) nest under a `(manual)` child — the tree normalizes distinct run URIs by stripping the `/<name>.schedule` suffix to group all of a workflow's runs under one node. The Manage Schedules tab fetches all owner schedules and filters client-side by that prefix (with a fallback for pre-existing schedules whose name was just the workflow name). The Runs tree's workflow-node right-click context menu (`WorkflowRunsContextMenu` / commands in `WorkflowRunsCommandContribution`) opens the editor (chaining a one-shot `pendingAction` onto the open via `WorkflowEditorWidgetOptions`), runs, schedules/manages, pauses/resumes all of a workflow's schedules, cancels active runs, refreshes, and copies the workflow path; all actions read the selected `WorkflowNode` from the tree model. Specs: `yarn workspace @continuum/workflow-editor-extension test`; `jsdom` is a devDependency because `SvgSanitizer.spec.ts` needs a DOM, and the file FAILS when jsdom is missing (set `ALLOW_NO_JSDOM=1` to run without it). Git support follows the official Theia IDE (Blueprint): `@theia/scm` + `@theia/scm-extra` (the Source Control view) is populated by the VS Code `git` + `git-base` extensions running on `@theia/plugin-ext` + `@theia/plugin-ext-vscode`; there is no `@theia/git`. The extensions are declared in `continuum-workbench/package.json` `theiaPlugins` (Eclipse-built `eclipse-theia/vscode-builtin-extensions` release assets) and fetched into `plugins/` by `yarn download:plugins`. Use the Eclipse builds, not old open-vsx ones: open-vsx `vscode.git` 1.88 implements an older SCM history API and fails to open repositories (`provider.onDidChangeCurrentHistoryItemRefs is not a function`). `plugin-ext` transitively re-introduces `@theia/debug` and `@theia/test`, so the Debug, Testing, and Outline widgets are all hidden by `HideUnwantedWidgetsContribution` on startup (unregisters their toggle commands in `onStart`, closes them in `onDidInitializeLayout`); `@theia/ai-ide` stays removed — the AI chat window and Ollama provider are bound by `@theia/ai-chat-ui` / `@theia/ai-ollama` with `@theia/ai-core`'s default `AIActivationService`. The Welcome widget (`src/browser/widgets/welcome/ContinuumWelcomeWidget.ts`) Help links: Documentation and Node Development open `https://docs.projectcontinuum.org` (Node Development → `/docs/contributing/create-new-nodes`) in a new tab; Keyboard Shortcuts executes `keymaps:open`, provided by `@theia/keymaps` `1.74.1` (pinned with the other VCS packages), which self-registers the keybindings widget and a default `Ctrl+Alt+,` keybinding |
| `workflow-builder-extension/` | `@continuum/workflow-builder-extension` | Theia AI chat agent "WorkflowBuilder" — a prompt only: discovers nodes, validates and builds the `.cwf` with api-server MCP tools, saves it with Theia's `writeFileContent` live (empty file first, rewritten after each added node); `claude-code/` has the Claude Code twin |
| `continuum-workbench/` | `@continuum/workbench` | Full Theia IDE app (port 3002) |
| `continuum-workbench-thin/` | `@continuum/workbench-thin` | Lightweight variant |

## Build

```bash
yarn install && yarn build && yarn start:workbench
# Open http://localhost:3002
```

## CI

`.github/workflows/ci.yml` runs on every pull request and push to `main`: `yarn install --frozen-lockfile --ignore-scripts` then `yarn test` (the specs of `workflow-editor-extension` and `workflow-builder-extension`; the other workspaces have none). `--frozen-lockfile` fails when `package.json` and `yarn.lock` disagree, so a dependency added without committing the lockfile cannot pass. Do not set `ALLOW_NO_JSDOM` in CI. Image builds and publishing stay in `build-module.yml` and `on-release.yml`.

## Stack
